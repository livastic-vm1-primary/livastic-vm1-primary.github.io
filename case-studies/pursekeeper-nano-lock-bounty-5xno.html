The real bug: read–compare–unlink is not one atomic step

A wallet client used a per-account local file lock to prevent two processes from operating the same wallet simultaneously. The file contained a holder PID and timestamp. If the PID was proven gone, another process could reclaim the stale record. But two waiters could interleave between a stale-file check and a later unlink.

  1. H is the old, dead process. Both waiting clients B and C read the lock record belonging to H.
  2. B compares that record, removes H's stale lock, creates a new live lock and enters the wallet critical section.
  3. C, acting on its earlier comparison, can now delete B's live lock and create its own lock.
  4. B and C may then both believe they own exclusive wallet access. The safety issue is concurrent writers, not merely an untidy file.

Checking the holder PID before unlinking is insufficient without mutual exclusion over the whole recheck-and-remove sequence. The sponsor's original discussion and deterministic regression are publicly auditable in issue #92 and the PR #94 diff.

What changed

For the same-host, cooperative local-file client, the repair introduced a distinct adjacent .reaper gate created with an exclusive filesystem-create flag (wx, equivalent to no clobber). Only the gate owner re-reads the dead-holder record, checks the holder is still gone, and unlinks that precise stale record. There are no remote calls, work generation, waits or signing within this synchronous gate section. The local tests also require no payment from a wallet.

When a gate already exists, another client does not steal or expire it based on age. It waits within the caller's configured bound and then refuses unsigned with exit status 5, identifying both lock and gate paths. An orphaned gate requires an operator to inspect processes before manual cleanup. This is a deliberate fail-closed availability versus exclusivity trade-off. PID reuse, independent machines and distributed storage are outside this local protocol's guarantees.

The original 4 changed files are source-visible, including wallet-lock-reaper.js and its synthetic local-file tests. This does not claim protection for other wallet software or distributed consensus.

How it was verified — without paying from a wallet

Deterministic fail-before / pass-after

A pre-existing exclusive reaper gate beside a dead holder's record forces the old client to take the wrong path. After the fix, the live client refuses unsigned, leaves the original dead record in place and identifies both files. The maintainer independently checked the new test against the old baseline and merged the repair.

With Node.js 24.20.0, the project executed 187 tests: 182 passed, 0 failed and 5 pre-existing environment skips. The same pass/skip totals were obtained locally with Node 22. This is actual software-test evidence, not 187 real payment transactions.

32 local mock repetitions

The race-case test for three simultaneous clients on one stale record was run in 32 separate Node 24 mock child processes: 32 passed, 0 failed. The runs used synthetic filesystem fixtures and localhost mocks; no independent third-party payment, Nano block or wallet signature was created by these tests.
